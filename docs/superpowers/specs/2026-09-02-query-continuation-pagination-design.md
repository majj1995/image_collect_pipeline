# 继续搜索按查询组合独立翻页设计

## 目标

修复“继续搜索”在首批审核后没有产生新素材的问题。每个查询组合必须保留自己的分页进度，单条件任务在精确查询耗尽后仍有一次只使用用户明确关键词的补充查询。

## 已确认行为

- 分页进度的唯一维度是 `label + provider + variantName + query`，不是 provider 全局页码。
- 某组合首次请求第 1 页；再次继续搜索时，若上一页成功且至少有 1 条结果，则请求第 2 页，依次递增。
- “短页”不代表耗尽：只要结果非空，即使 `hitCount < requestCount` 也允许再尝试下一页。
- 空页代表该查询组合耗尽；达到 provider 的 `canRequestPage` 上限也立即停止。
- 同一 `label + provider + variantName + query + page` 不得重复创建。
- 每个 provider 的调度优先级是：已执行查询的下一页 → 未执行基础组合 → 未执行补充组合。
- 不支持分页的 provider 不会伪造第 2 页，而是进入下一个未执行查询组合。
- 中英文 profile 各只有 1 个 term 和 1 个 style 时，补充波使用“仅 term + 用户显式 required/excluded constraints”；不发明新关键词。
- 一般的“继续搜索”不自动重试终止失败的 provider run；只有“重新尝试该来源”才传入 `retryFailedProviderIds`。
- 失败 run、可恢复 run 或图片物化任务只能阻塞它们自身的查询组合，不得全局阻塞其他新页或新组合。
- 已拒绝候选不再进入下载恢复队列，也不会重开签名 URL 查询。
- API 异步启动搜索后，若轮询到终态时候选集合没有新 ID，页面显示“本轮未新增素材；已选来源或查询可能已耗尽，请增加来源或调整条件。”
- 来源选择按任务保存在本地浏览器中；重新进入任务后恢复仍然存在且可用的来源，不能静默替换成默认来源。
- 平台返回的原始命中数独立持久化，不能因其它并发来源先填满候选批次而误判本组合为空。
- provider 失败形成的 `retryable` run 必须持久标记为仅显式重试；本地中断、暂停和下载恢复仍可由普通继续搜索恢复。
- Wikimedia 只在显式配置可安全用作 HTTP 头且包含联系 URL、邮箱或 Wikimedia `User:` 用户名的 `WIKIMEDIA_USER_AGENT` 后启用；搜索和下载使用同一值。图片下载按单来源串行调度，并遵循 429 `Retry-After`；缺失响应头时使用 provider 级指数退避，冷却等待不占用单次网络超时，外部取消会取消等待并回滚未消费的请求起点预留。
- 2,000 个 run 的单轮上限必须跨 provider 轮转分配；同一 provider 中已创建的 `page > 1` 续页不得被 page-one 暂停积压或未执行基础查询越过，显式重试积压也必须给合法续页保留持续进度。
- 被拒绝候选在命中入队、物化目标、最终 claim 和启动恢复四层均不得下载；若用户恢复了曾被 worker 跳过的候选，必须持久标记可恢复状态，并在旧 worker 完成后可靠重排。拒绝态自身不得触发前端无限轮询。

## 真实任务边界

`0784c484-e84b-41ff-b381-ccb28ec9c3f6`（电动牙刷素材收集）中，百度不支持分页，Openverse/Wikimedia 的第 1 页为空，Bing 已终止失败。因此分页修复不会伪造百度第 2 页；该任务的下一个合法发现工作是中英文各自的 term-only 补充查询。

真实回归中，Wikimedia 的 `term_only` 已依次创建第 1、2、3 页，百度创建中文 `term_only` 第 1 页；候选数从 26 增至 199，且没有重复查询页键。真实回归还暴露并修复了页面重载换源、普通继续隐式重试 Openverse，以及 Wikimedia 下载 429 被整批快速耗尽的问题。

## 验证

- 使用无网络 fake provider 验证查询组合独立翻页、短页继续、空页停止、provider 上限停止和 run key 去重。
- 规划器单元测试验证 singleton term-only 查询只含用户输入。
- 服务端集成测试验证终止失败和已拒绝下载恢复不阻塞新发现。
- 前端测试验证 `collecting → terminal` 且候选 ID 不变时出现零新增提示。
- 全量测试、TypeScript 类型检查和生产构建通过后，再使用真实任务进行本地浏览器回归。
