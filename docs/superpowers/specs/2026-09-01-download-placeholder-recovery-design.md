# 下载占位恢复设计

## 背景与根因

候选卡片上的“下载未完成”不是浏览器图片元素的普通加载错误，而是服务端在素材下载重试耗尽后写入的终态。当前实现将 HTTP 403、HTTP 429、网络超时和其他上游失败全部压缩成 `pipeline_error = 'RETRYABLE_DOWNLOAD'`，因此前端只能给出笼统且可能错误的“网络恢复”提示。

本地数据中绝大多数此类候选来自 ARTIC。其 IIIF 图片端点在当前代理与直连环境中均返回 HTTP 403；同时 ARTIC 官方要求图片串行抓取并建议相邻下载间隔约一秒，而现有素材队列允许四路并发且没有来源级节流。另一个放大因素是搜索命中已经保存 `thumbnail_url`，但主图失败后从未使用该缩略图兜底。

## 已确认方案

1. 保留 `pipeline_error = 'RETRYABLE_DOWNLOAD'` 作为人工重试状态，另存白名单失败分类 `FORBIDDEN | RATE_LIMITED | NETWORK | GENERIC`。前端只展示这些安全分类的固定中文文案，不展示 URL、响应体或原始异常。
2. 主图的可下载失败耗尽后，尝试同一提供方搜索命中中保存的缩略图。缩略图必须经过与主图完全相同的 DNS/SSRF、重定向、大小和媒体格式校验。
3. ARTIC 图片下载使用单并发并保证每次远程图片请求的开始时间至少间隔 1000ms。搜索服务的素材队列按提供方限制活跃任务数并跳过暂不可启动的队首候选；素材服务在每次主图重试和缩略图请求前执行间隔门控。这样至多一个 ARTIC 任务占用全局素材槽，其他提供方仍可占用剩余的全局四路容量。
4. “继续搜索”对稳定图片地址的提供方直接重新排队已有 `RETRYABLE_DOWNLOAD` 候选，不依赖搜索结果再次返回这些候选。Snap Ads 与 TikTok Ads 的短期签名地址仍重放原查询，以取得新签名后再下载。
5. 候选卡片根据安全失败分类展示真实原因。已处理素材的本地缩略图若返回 404 或无法解码，卡片显示可见占位，不保留破图元素。

## 兼容与恢复

- 已有数据库通过增量列迁移获得 nullable `pipeline_failure_code`；既有失败行保持 null，并显示通用可重试提示。
- 成功处理、重新 claim、隔离、无效、缓存重建和服务重启恢复都会清除不再适用的失败分类。
- 当前 ARTIC 403 不保证在修复后立即恢复；修复的目标是避免继续高频请求、尝试缩略图兜底，并准确说明来源拒绝下载。
- 不新增运行时依赖，不改变既有双语查询、审核、导出或授权流程。
